# Dynamic artwork — current implementation and earlier handset validation

Updated 2026-10-11 (Europe/Paris). The selected Premiere presentation and VLC engine are retained.

Artwork lookup now starts automatically from VLC's scanned video/audio library. The complete array is processed in bounded background work through the same cache and matching pipeline used for visible cards. A newer scan interrupts the current pass and is picked up first; media-library IDs prioritize newly added items. The sweep resumes at the next application start, and settings, metadata changes, cache clearing, and transient network retries re-queue candidates. Music chooses the closest plausible match instead of requiring a unique exact title. Visible artwork jobs move ahead of background jobs in both metadata and network queues. Movie matches retain their title/year safeguards. Current build and handset evidence is recorded in VERIFICATION.md.

## Actual matching behaviour

`native/org/videolan/vlc/premiere/Artwork.java` resolves artwork from actual Medialibrary items. Storage reads, metadata extraction, decoding and HTTP run in bounded background executors. Movie cards are portrait 2:3; album/player covers are square. Cards play media directly; the Actions menu retains Media information. Display options can switch to a compact list.

Both VLC metadata and embedded title/artist/album/album-artist/year tags are read. Filenames supply fallback titles, release years and episode clues. Video cleanup removes container/codec/quality suffixes while preserving numeric titles such as 1917 and 2001: A Space Odyssey. A clear title conflict suppresses matching. Camera names such as VID_YYYYMMDD skip catalogue lookup.

Audio cleanup removes leading track/disc indexes and recognises artist/title separators, including multiple spaces. For example, the real phone file `001 - DJ shadow   Organ Donor.mp3` has no title, artist or album tags; its filename supplies DJ Shadow + Organ Donor. Tag values can supply the artist for a title-only filename. VLC can expose the full filename including .mp3 as its title; this is recognized as filename fallback, not a contradictory embedded title. Title-only files are searched too, with candidates ranked by fuzzy title similarity. Artist identity increases confidence when available.

Fuzzy ranking combines character edit distance and token similarity, normalises Unicode/punctuation/case, and rejects conflicting numeric sequels. Known movie-year conflicts are rejected. Provider identities are deduplicated. Movie matching requires a lead over the runner-up; music selects the highest plausible score and keeps alternate images so duplicate uploads do not suppress coverage. No first-result shortcut or fixed movie/album/video IDs are used.

TMDB movie/TV searches use configuration-derived image sizes/base URLs. MusicBrainz searches tagged album + artist first; when the album is unknown it searches recording title + artist, then ranks the returned release groups. A clear original studio album is preferred over singles, compilations, soundtracks, live recordings and bootlegs. For an untagged song this is a representative album cover, not a claim that the source file came from that exact release. MusicBrainz calls are at least 1.1 seconds apart. CAA uses its front-500 endpoint and follows bounded HTTPS redirects to Internet Archive. Deezer provides an independent public music catalogue fallback when MusicBrainz is unavailable or has no usable image. Artist releases provide representative art only when no closer song/source match is available.

YouTube thumbnails are preferred for live sets and used before representative artist art for other songs. Public HTTPS search results are parsed through a bounded ytInitialData JSON extractor; no JavaScript is evaluated. Artist/title, venue and date clues rank videoRenderer candidates. Known video URLs or bracketed IDs can resolve directly. Search requests are spaced by at least 1.1 seconds and deduplicated through the existing query/entity caches. Thumbnail URLs are restricted to the HTTPS i.ytimg.com host. No YouTube key, login or cookies are needed. Consent pages, request failures or changed public search markup fall back to the other sources; public page markup is a maintenance dependency. Existing representative/live covers remain visible while a source-image upgrade is attempted, including when online lookups are disabled.

## Cache and settings

More → Settings → Artwork provides a masked TMDB read-token field, provider lookup switches, cache clearing and retrying missing artwork. The token is validated and saved atomically only in app-private `noBackupFilesDir`, never shipped in the APK. Save & enable also enables movie lookup. It survives restarts and update installation; uninstalling or clearing app data removes it. Authorization headers are restricted to the TMDB API host; redirects cannot forward that token to image/music hosts. About/Credits includes the approved TMDB logo, exact required notice and links to TMDB, MusicBrainz, Cover Art Archive, Deezer and YouTube.

App-private cache records contain media fingerprints, provider identity, matched title/query/year, confidence and timestamps; local paths and credentials are excluded. Media fingerprints include URI-derived identity, size/modified time and metadata. Query and entity records deduplicate shared movies/albums. Writes are atomic, decoded RAM is capped at 16 MiB, disk cache at 64 MiB / 4096 entries, and disk records expire after 90 days. Catalogue misses retry after one day; offline/transient failures are not saved as long catalogue misses. Cached images are read before checking online switches. Medialibrary callbacks are coalesced and compared using stable URI/ID/tag/file signatures. Unchanged callbacks skip page reconstruction and artwork invalidation. Genuine content changes invalidate RAM, restart the artwork sweep and retain scroll and pagination state on the current screen. Explicit artwork retry/settings actions still restart the full sweep. Movie and music requests have separate queues so a music backlog cannot block posters.
